# 从玻璃材质到视觉与交互体系

状态：演进设计草案，2026-11-10。以下新增规范和任务尚未等同于可用 API；现有动画实现的设备验收继续独立跟踪。

## 定位

让调用者用同一套视觉语言组织完整 Flutter 界面：信息层级、内容密度、空间、材质、导航、输入、反馈和状态转换。玻璃是其中一种材质，应服务于层级和上下文关系，而不是覆盖所有内容。

Windows 桌面与 Android 移动端均纳入设计与验收。保留 Android 优先的性能约束；桌面需要单独覆盖窗口尺寸、DPI、鼠标、键盘和窗口焦点。保留纯 Flutter、无业务耦合、无第三方 UI 运行时依赖的边界。

## 现有基础与缺口

| 领域 | 已有公开能力 | 下一步缺口 |
| --- | --- | --- |
| 材质 | GlassStyle、GlassPresets、GlassSurface、GlassGroup | 何时使用不透明内容区、轻透明容器和浮层；嵌套与阅读规则 |
| 主题 | LiquidGlassThemeData，兼容 ThemeData.extensions | 语义颜色、间距、圆角、层级与密度的一致表达 |
| 交互 | 卡片/按钮的按压、hover、focus、禁用与指针高光 | 选中、展开、忙碌、校验、键盘导航等模式的组合契约 |
| 动效 | GlassMotionSpec、GlassPageRoute、对话框过渡 | 不同场景何时用哪种过渡；如何表达状态连续性 |
| 降级 | 质量、减少动画、高对比度、减少透明度与无模糊 | 同一完整场景在各降级设置下仍可辨认、可操作 |
| 示例 | 材质 Gallery 与组件演示 | 可运行的完整任务流、窗口适配和分层 API 教程 |

## 视觉规则

先选择界面角色，再选择材质和数值。第一轮只定义少量、用途明确的角色：

| 角色 | 表现与用途 | 降级要求 |
| --- | --- | --- |
| 背景 | 安静的底色或静态柔光，承载整体氛围 | 不依赖运动或模糊才能辨认内容 |
| 内容 | 正文、输入、列表、表格和高密度信息优先稳定底色 | 长文本、选中、错误与禁用仍可读 |
| 容器 | 聚合同类信息，以留白、边缘和轻透明度区分组别 | 关闭透明度后仍能看出分组 |
| 浮层 | 菜单、命令面板、对话框，表达临时层级与上下文 | 明确边界、遮罩、焦点与关闭方式 |

不把 elevation、透明度和模糊混为一个深度旋钮；提升层级不必提高 sigma。避免每个列表项都独立模糊，重叠过滤继续遵守 backdrop key 隔离规则。高光限制在边缘，不覆盖阅读内容。

颜色用正文、次级文字、分隔线、强调、选中和错误等语义表达。字体优先复用 Flutter TextTheme，方向性间距使用 EdgeInsetsDirectional。间距与圆角先在示例中验证一套短刻度，不立即增加一组永久公开常量。紧凑布局不能缩小已承诺的触控目标，文本放大不能隐藏主要操作。

## 交互契约

| 场景 | 必须定义的行为 |
| --- | --- |
| 导航与选中 | 当前项、hover、键盘焦点分别表达；选中不只依赖颜色；选择、激活和切换页面不混用 |
| 浮层 | 打开后的焦点位置、Tab 范围、Escape/返回关闭、关闭后恢复焦点、遮罩点击策略 |
| 表单与反馈 | 标签、帮助、错误、提交中与重复触发策略；忙碌状态不能让布局跳动或丢失焦点 |
| 列表与详情 | 列表焦点与详情内容关联，加载/空/错误各自有恢复路径；不内置业务模型或网络层 |
| 桌面 | 鼠标与键盘均可到达主要操作，窗口失焦与重新聚焦不残留按压，滚轮与快捷键不劫持系统约定 |
| 移动端 | 不依赖 hover 才出现必要操作；触摸取消、返回和软键盘不遮住关键操作 |

按压/焦点仍遵循现有 ANIMATION_SPEC.md。导航箭头、快捷键、Escape 与焦点恢复优先复用 Flutter 的 Focus、Actions、Shortcuts 和路由能力。仅对需要的组件启用拖拽，不增加全局手势拦截。减少动画时保留清晰的即时状态提示。

## API 使用路径

让不同熟练度的调用者都能找到入口，但保持一套实现来源：

1. 先体验完整场景：示例展示界面如何分区、如何输入、如何从列表进入详情与关闭浮层。
2. 再复制组合配方：使用现有主题、表面、布局和 Flutter 标准导航/输入部件，替换自己的数据与内容。
3. 最后按需调整材质：通过已有 GlassStyle 和局部主题覆盖细节，不要求应用从 blurSigma 等底层参数开始搭建界面。

配方默认是可阅读的示例代码，不默认成为公开 Scaffold、Router、Controller 或状态管理框架。主题扩展优先沿用 LiquidGlassThemeData；不同时引入第二套 Theme 或重复的 Token 注册机制。新增语义配置必须完成 copyWith、lerp、局部覆盖与默认值兼容设计。

仅当两个不同场景出现同一段难以正确组合的行为，且现有公开能力无法表达时，才提炼公开类型。名称、参数、默认值和导出需单独评审；本文没有承诺任何尚未实现的类名。

## 第一条完整场景：可适配的工作区

使用无业务含义的本地示例数据，不加入账户、网络或文件持久化：

- 宽窗口：导航区、内容列表与详情区并排；工具栏和临时浮层体现材质层级，阅读区保持稳定底色。
- 窄窗口：导航收拢，列表与详情按页面切换；保留选择上下文和可达的返回入口。
- 至少完成一条流程：查找项目 → 选择 → 查看详情 → 打开临时操作面板 → 关闭并返回原焦点。
- 同一数据与选择状态在改变窗口宽度后保留；断点根据内容空间决定，不使用 platform == Windows 决定布局。
- 展示一套默认主题和一套覆盖后的主题，证明调用者能改变视觉语言，而不是只能更换玻璃预设。

先通过该场景检验规则，再决定是否扩展更多组件。场景中的加载/空/错误由本地可控状态展示，不把模拟延时当作真实后端。

## 阶段与验收

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| V1 规则与主题试验 | 角色、密度与语义色的示例映射；复用现有 ThemeData/TextTheme | 两套主题、浅深色、文本放大和降级下层级可辨；再决定需要公开哪些配置 |
| V2 完整工作区 | 可运行的宽/窄窗口场景与上述完整流程 | 不丢选择状态；键盘、触摸均可操作；不引入业务依赖 |
| V3 行为模式 | 浮层焦点恢复、导航选择与反馈规则及回归 | 实际事件测试覆盖 Tab、Escape/返回、取消、失焦及减少动画 |
| V4 API 与指南 | 从场景到配方到材质的文档；基于复用证据提炼接口 | 旧示例仍能编译，新 API 有文档、测试和导出；未提炼也需说明理由 |
| V5 平台验收 | Windows EXE/窗口/DPI 与 Android 模拟器功能、目标真机性能记录 | 分开记录工具测试、真实应用和硬件数据，不因设计规则写完而宣称平台完成 |

Windows 应检查 100%/150%/200% 缩放、改变窗口大小、滚轮、键盘遍历与窗口失焦；Android 检查触摸取消、返回、软键盘和文本放大。两端均检查高对比度、无模糊、减少透明度、减少动画和空闲 ticker。实际运行条件不存在时保留未完成项。

## 兼容性与暂缓项

现有包名、统一导出、Glass* API 与默认视觉继续保持兼容；这份设计不进行重命名或强制迁移。旧动画任务和设备验收不被新路线覆盖。视觉体系不以 Shader 为前提，可选折射仍遵守 Impeller、明确降级和真机 profile 的原有边界。

本阶段不创建庞大的全组件清单，不引入路由/状态管理依赖，不实现业务工作台或操作系统级窗口材质。API 的扩充必须来自可运行场景中的需要。
